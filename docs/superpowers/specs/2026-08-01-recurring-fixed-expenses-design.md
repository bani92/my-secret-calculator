# 반복 고정비 자동 생성 설계

## 목표

매달 반복되는 고정 지출을 한 번 등록해두면, 사용자가 앱을 열었을 때 오늘 날짜까지 발생했어야 하는 항목을 실제 지출로 자동 생성한다.

예를 들어 `매달 1일 동양생명 10,000원`, `매달 5일 자동차보험 30,000원`을 등록해두면 2026-08-01에 앱을 열었을 때 동양생명만 생성되고, 2026-08-05 이후에 앱을 열면 자동차보험도 생성된다.

고정비 규칙은 앞으로 생성될 지출의 원본이고, 이미 생성된 지출은 그 시점의 실제 기록으로 유지한다. 따라서 2026-08-25에 동양생명 규칙 금액을 20,000원으로 수정해도 2026-08-01 지출 10,000원은 유지되고, 2026-09-01부터 20,000원이 생성된다.

## 선택한 방향

새 탭 `고정비`를 추가한다.

- `입력`: 당일 지출과 수입을 직접 기록한다.
- `고정비`: 반복 고정비 규칙을 추가, 수정, 삭제 또는 비활성화한다.
- `대시보드`, `통계`, `캘린더`: 자동 생성된 고정비를 일반 지출처럼 보여준다.

자동 생성은 서버 스케줄러 없이 앱 데이터 로드 후 실행한다. 현재 앱은 Vue 3, Pinia, Supabase 중심 구조이므로 별도 Spring Boot 백엔드나 클라우드 스케줄러를 처음부터 두지 않는다. 나중에 앱을 열지 않아도 정해진 날짜에 생성되어야 하는 요구가 생기면 Supabase Edge Function 또는 Spring Boot 스케줄러로 확장할 수 있다.

## 자동 생성 기준

앱 로그인 후 예산 데이터를 로드하면 다음 순서로 자동 생성을 시도한다.

```text
오늘 날짜 확인
→ 현재 월의 반복 고정비 규칙 조회
→ 반복일이 오늘 일자 이하인 활성 규칙만 선택
→ 같은 규칙이 같은 월에 이미 생성됐는지 확인
→ 아직 없으면 실제 지출로 추가
```

예시는 다음과 같다.

```text
오늘: 2026-08-01
매달 1일 동양생명 10,000원 → 생성
매달 5일 자동차보험 30,000원 → 생성 안 함

오늘: 2026-08-02
매달 1일 동양생명 10,000원 → 이미 8월분이 있으므로 건너뜀
매달 5일 자동차보험 30,000원 → 생성 안 함

오늘: 2026-09-05
매달 1일 동양생명 20,000원 → 9월분이 없으면 생성
매달 5일 자동차보험 30,000원 → 9월분이 없으면 생성
```

처음 구현에서는 현재 월 기준으로만 자동 생성한다. 예를 들어 9월에 앱을 한 번도 열지 않고 10월 3일에 앱을 열면 10월 1일 항목은 생성하지만, 9월 항목을 소급 생성하지 않는다. 월 단위 소급 생성은 사용자가 원할 때 별도 기능으로 추가한다.

## 데이터 모델

반복 규칙과 실제 지출을 분리한다.

```ts
export interface RecurringFixedExpenseRule {
  id: string;
  dayOfMonth: number;
  categoryId: CategoryId;
  amount: number;
  memo: string;
  active: boolean;
  createdAt?: string;
  updatedAt?: string;
}
```

기존 `Expense`에는 자동 생성 출처를 추적하기 위한 선택 필드를 추가한다.

```ts
export interface Expense {
  id: string;
  date: string;
  month: string;
  categoryId: CategoryId;
  amount: number;
  memo: string;
  createdAt?: string;
  recurringRuleId?: string;
}
```

`BudgetData`에는 반복 규칙 배열을 추가한다.

```ts
export interface BudgetData {
  version: 1;
  months: Record<string, MonthRecord>;
  expenses: Expense[];
  incomeRecords: IncomeRecord[];
  personRecords: PersonMoneyRecord[];
  recurringFixedExpenseRules: RecurringFixedExpenseRule[];
}
```

기존 백업 JSON에는 `recurringFixedExpenseRules`가 없으므로 가져오기 시 빈 배열로 보정한다.

## Supabase 구조

새 테이블 `recurring_fixed_expense_rules`를 추가한다.

| 컬럼 | 타입 | 설명 |
| --- | --- | --- |
| `id` | `uuid` | 규칙 ID |
| `user_id` | `uuid` | 로그인 사용자 |
| `day_of_month` | `integer` | 매달 반복일, 1-31 |
| `category_id` | `text` | 지출 분류 |
| `amount` | `integer` | 0보다 큰 금액 |
| `memo` | `text` | 항목명 또는 메모 |
| `active` | `boolean` | 자동 생성 여부 |
| `created_at` | `timestamptz` | 생성 시각 |
| `updated_at` | `timestamptz` | 수정 시각 |

기존 `expenses` 테이블에는 `recurring_rule_id uuid null` 컬럼을 추가한다. 외래키는 같은 사용자 경계를 직접 강제하기 어렵기 때문에 앱 로직과 RLS로 관리하고, 중복 방지는 앱 로직에서 `recurring_rule_id + month` 조합을 확인한다.

RLS 정책은 기존 테이블과 동일하게 `auth.uid() = user_id` 기준으로 둔다.

`replace_budget_data` RPC는 반복 규칙과 `expenses.recurring_rule_id`를 함께 교체하도록 확장한다.

## UI

상단 탭에 `고정비`를 추가한다.

고정비 탭의 기본 구성은 다음과 같다.

```text
[+ 고정비 추가]

매달 1일   동양생명       10,000원   고정비   활성   [수정] [삭제]
매달 5일   자동차보험     30,000원   고정비   활성   [수정] [삭제]

이번 달 자동 생성 상태
- 8월 1일 동양생명 생성됨
- 8월 5일 자동차보험 예정
```

추가와 수정 폼은 다음 값을 받는다.

- 반복일: 1-31
- 분류: 기존 지출 분류 중 선택, 기본값 `고정비`
- 금액: 0보다 큰 금액
- 항목명 또는 메모
- 활성 여부

삭제는 사용자가 자유롭게 할 수 있게 제공한다. 삭제한 규칙은 앞으로 자동 생성되지 않는다. 이미 생성된 과거 지출은 삭제하지 않는다. 과거 지출은 입력 탭의 거래 내역에서 일반 지출처럼 수정 또는 삭제할 수 있다.

비활성화는 삭제하지 않고 잠시 자동 생성만 멈추고 싶을 때 사용한다.

## 배포 전 화면 검수

구현이 끝나면 배포하기 전에 데스크톱과 모바일 화면 시안을 먼저 만든다. 사용자가 배포 후 모바일에서 확인하며 다시 수정하는 일이 줄어들도록, 최소한 다음 화면을 확인한다.

- 데스크톱 고정비 탭
- 모바일 고정비 탭
- 데스크톱 입력 탭의 자동 생성 지출 표시
- 모바일 입력 탭의 자동 생성 지출 표시

시안은 실제 구현 화면을 기준으로 캡처하거나, 필요한 경우 HTML 목업으로 만든다. 모바일 기준은 360px과 390px 폭을 우선 확인한다. 텍스트가 버튼이나 카드 밖으로 넘치지 않는지, 고정비 목록의 날짜, 항목명, 금액, 수정/삭제 버튼이 겹치지 않는지 확인한 뒤 배포한다.

## 예외 처리

반복일이 29-31일인 경우 해당 월에 그 날짜가 없을 수 있다. 처음 구현에서는 해당 월에 존재하는 날짜일 때만 생성한다. 예를 들어 매달 31일 규칙은 9월에는 생성되지 않고, 10월 31일에는 생성된다.

자동 생성 중 일부 항목 저장이 실패하면 화면 상단 상태 메시지로 실패를 알린다. 이미 생성된 항목은 유지하고, 다음 앱 실행 때 아직 생성되지 않은 항목만 다시 시도한다.

같은 월에 사용자가 자동 생성된 지출을 직접 삭제한 뒤 앱을 다시 열면 중복 방지 기준만으로는 다시 생성될 수 있다. 이를 막기 위해 처음 구현에서는 삭제된 자동 생성 이력을 별도 저장하지 않고, 사용자가 해당 월만 원하지 않는 경우 생성된 지출을 금액 0으로 만드는 대신 직접 삭제하지 않는 사용 흐름을 안내하지 않는다. 이 문제는 실제 사용 중 필요가 커지면 `skipped_recurring_expense_occurrences` 같은 예외 테이블로 확장한다.

## 테스트

TDD로 다음 동작을 검증한다.

- 기존 백업 JSON에 `recurringFixedExpenseRules`가 없으면 빈 배열로 보정한다.
- 고정비 규칙을 추가, 수정, 삭제, 비활성화할 수 있다.
- 오늘 날짜보다 반복일이 크면 자동 생성하지 않는다.
- 오늘 날짜 이하의 활성 규칙은 해당 월 지출로 자동 생성한다.
- 같은 규칙이 같은 월에 이미 생성된 경우 중복 생성하지 않는다.
- 규칙 금액을 수정해도 이미 생성된 과거 지출 금액은 바뀌지 않는다.
- 다음 달 자동 생성에는 수정된 규칙 금액이 적용된다.
- 비활성 규칙은 자동 생성하지 않는다.
- Supabase 저장소가 반복 규칙과 `recurringRuleId`를 로드, 저장, 교체한다.
- 배포 전 데스크톱과 모바일 화면 시안을 확인한다.
- 전체 Vitest와 production build가 통과한다.

## 이번 범위에서 제외

- 앱을 열지 않아도 서버가 정해진 날짜에 자동 생성하는 기능
- 지난달에 앱을 열지 않았을 때 누락된 고정비를 소급 생성하는 기능
- 자동 생성된 지출을 삭제했을 때 해당 월만 다시 생성하지 않는 예외 이력
- 수입 반복 생성
- 주간, 연간, 격월 반복
- Spring Boot 백엔드 스케줄러
